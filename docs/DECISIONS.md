# Архитектурные решения

## 1. Выбор СУБД (задание 1.0, п.3) — PostgreSQL

**Характер данных.** Датасет — ~340 тыс. транзакций с фиксированными колонками: даты, категориальные
измерения (регион, штат, категория, канал…) и числовые меры (количество, цена, скидка, выручка).
Типичные запросы — фильтрация по нескольким полям и `GROUP BY` с агрегатами (`SUM`, `AVG`, `COUNT`),
в том числе по времени (`date_trunc`) и с соединением с макропоказателями по неделе.

**Почему PostgreSQL**
- Реляционная модель естественна для таких данных: типы `NUMERIC` (деньги без ошибок округления), `DATE`, ограничения и уникальные индексы.
- Сильный аналитический SQL: `GROUP BY`, оконные функции, `date_trunc`, `FILTER`, CTE.
- Богатые индексы (B-tree, составные, BRIN по дате, частичные) — достаточно для сотен тысяч и миллионов строк.
- `JSONB` для полей источника, не попавших в схему (колонка `extra`) — гибкость без отказа от схемы.
- Первоклассная поддержка в Django (ORM, миграции, `update_conflicts` для upsert), зрелый Docker-образ, бесплатная лицензия.
- Масштабирование при росте: партиционирование по дате, материализованные представления, реплики для чтения.

**Почему не другие**
| Вариант | Причина отказа |
|---|---|
| SQLite | Нет конкурентной записи, слабее типы и индексы; годится только для локальных тестов (поддержан флагом `DB_ENGINE=sqlite`). |
| MySQL/MariaDB | Подходит, но слабее аналитический SQL и поддержка JSON/индексов; в Django `update_conflicts` ограничен. |
| MongoDB | Схема фиксирована и табличная, нужны соединения и агрегации по измерениям — документная модель только усложнит. |
| ClickHouse / TimescaleDB | Лучше на миллиардах строк, но избыточны для 340 тыс. записей и хуже интегрируются с Django ORM/админкой. Разумный путь миграции при росте данных на порядки. |

## 2. Хранение макропоказателей (задание 1.1)

**Решение:** отдельная таблица `MacroIndicator` в **длинном формате** — одна строка = (`week_start`, `indicator`, `value`)
с уникальностью по паре (`week_start`, `indicator`). Связь с продажами — по ключу `week_start`
(понедельник недели), вычисляемому и для продаж, и для макро-данных. Внешнего ключа нет намеренно: продаж на неделю много,
а макро-значение одно; связь «многие к одному» по значению даты.

**Преимущества**
- Новые показатели добавляются без миграций схемы (пока источник расширяется — таблица не меняется).
- Загрузка идемпотентна (`upsert` по уникальному ключу), пропуски недель/показателей не создают «дыр» с NULL.
- Универсальные запросы: «все показатели за период», «средний показатель за месяц» — один и тот же код.
- Макро-данные не дублируются в каждой строке продаж (было бы ×340 тыс.).

**Недостатки и компромиссы**
- Для анализа «широкой» таблицы (показатели в колонках) нужен pivot — реализован в `/api/macro/weekly/`.
- Нет единой схемы типов/единиц: все значения `float`, единицы измерения не хранятся (улучшение: справочник `Indicator` с единицами и описанием).
- Соединение с продажами по значению даты, а не по FK: целостность обеспечивается единым способом вычисления `week_start`.
- Строк больше, чем в широкой таблице (недель × показателей), но объём тривиален.

**Альтернативы:** широкая таблица (быстрее для фиксированного набора, но миграция на каждый новый показатель);
JSONB-колонка на неделю (гибко, но хуже индексируется и агрегируется).

## 3. Прочие решения
- **Колонки `extra` (JSONB):** импорт не теряет поля, которых нет в схеме.
- **`week_start` + `date`:** исходная дата сохраняется, ключ для соединения вычисляется.
- **Отключён `COUNT(*)` в админке** (`show_full_result_count = False`) и кэшируются значения выпадающих фильтров — иначе большие таблицы тормозят.
- **Общий слой агрегаций** (`sales/services/aggregation.py`) используется API, дашбордом и xlsx-отчётом — одна логика, нет расхождений цифр.
